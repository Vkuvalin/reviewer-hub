# Заключение Reviewer: сначала проверить набор, затем применять

**Вывод:** сопоставление по `photo_id` необходимо, но проверки количества строк недостаточно. До первой записи нужно проверить весь ответ относительно отправленного набора.

## Основания

| Источник | Наблюдение |
|---|---|
| [Принятый контракт](DISCUSSION.md#принятый-контракт) | Каждая ожидаемая фотография должна встретиться ровно один раз |
| [`apply_sequentially`](repository/quality.py) | Запись вызывается внутри обхода ответа до полной проверки набора |
| [Прогон](replay.py) | Для ответа `front, back, front` возникают три вызова записи, хотя `mark` отсутствует |

Даже добавленная проверка длины пропустит такой ответ: ожидаемых фотографий три, оценок тоже три. При этом одна фотография обработана повторно, а другая не представлена. Аналогично нужно отклонять неполный набор и ID, не принадлежащий текущему запросу.

Это разрыв между правилом целого набора и обработкой отдельных элементов.

## Рекомендация

Разделить обработку на две фазы:

1. Проверить форму оценок, принадлежность ID текущему набору, отсутствие повторов и точное совпадение с ожидаемым составом.
2. Подготовить изменения и применить весь корректный набор в короткой транзакции реального хранилища.

[`apply_after_validation`](repository/quality.py) показывает первую границу: невалидный ответ отклоняется до вызовов записи. Транзакционная граница при интеграции дополнительно защищает от сбоя самого хранилища.

| Критерий | Ожидаемый результат |
|---|---|
| Корректный набор в любом порядке | Все три оценки сопоставлены по ID |
| Пропуск, повтор или посторонний ID | Ответ отклонён, вызовов записи — 0 |

## Следующий шаг

Передать замечание Executor как ограниченную задачу: добавить предварительную проверку и закрепить перечисленные случаи. Принятие изменения остаётся у пользователя и Command Center.

Reviewer завершает исследование: для этого вывода достаточно контракта и обработчика; весь проект и полную историю читать не требуется.
