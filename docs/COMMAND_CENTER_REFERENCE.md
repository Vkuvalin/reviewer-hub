# Command Center — справочник Reviewer

Status: compact Reviewer reference, non-canonical.

Канонический источник: подтверждённый репозиторий Command Center, указанный в памяти активного проекта.

При конфликте канонический репозиторий имеет приоритет. Этот справочник объясняет внешнюю систему Command Center, но не является её источником истины и не переносит её процесс работы внутри репозитория в ReviewerHub.

## Участники и ответственность

- Пользователь — задаёт цель, приоритеты и ограничения, принимает или отклоняет результат; окончательная человеческая точка решения.
- ChatGPT / Command Center — основной архитектурный и синтетический контур: помогает формировать архитектуру, ведёт Stage Plan, следит за границами работы и принятыми решениями, ставит задачи Codex и проводит Review. За архитектуру и её утверждение отвечает Command Center.
- Codex Executor — локально исполняет явную задачу в разрешённых границах и по правилам целевого репозитория; возвращает результат и проверяемые материалы.

Reviewer существует рядом с этой системой и не является её новой постоянной фазой.

## Stage / Step / Step-loop

- `Stage` — крупный блок работы с целью, границами и картой вопросов.
- `Step` — конкретный вопрос, решение или участок работы внутри Stage.
- `Step-loop` — любое необходимое число уточнений внутри одного Step. Пока вопрос не закрыт, работа остаётся в этом цикле.

Верхнеуровневый Stage Plan задаёт направления, примерные вопросы и ожидаемые итоги, а не полный заранее фиксированный список Step. `Stage 0` может использоваться для формирования цели и предварительной карты; `X.0` — для уточнения границ конкретного Stage. Состав Step уточняется при входе в Stage и по мере появления фактов.

## Gate и Decision gate

`Gate` — явное закрытие текущего Step: решение сформулировано и зафиксировано, можно переходить к следующему вопросу. Он фиксируется внутри Step, а не как отдельная фаза `Phase loop`.

`Decision gate` — отдельная фаза сборки и проверки решения всего Stage. Command Center сводит решения закрытых Step, проверяет совместимость и выбирает: принять сборное решение, отправить его на необязательный Codex Audit или вернуть конкретный вопрос в Step-loop.

Закрытый Gate одного Step не означает принятия решения всего Stage. Поле `Decision gate` в навигационной плашке показывает условие перехода и трактуется с учётом текущей фазы, как описано ниже.

## Phase loop

`Phase loop` показывает, что сейчас делается, а не зрелость архитектуры.

| Фаза | Смысл |
|---|---|
| `Stage framing` | Уточнение цели, границ, вопросов Stage и начального состояния `Architecture`. |
| `Step discussion` | Обсуждение текущего Step через Step-loop до его Gate. |
| `Decision gate` | Сборка решения Stage и выбор дальнейшего перехода. |
| `Codex Audit` | Необязательная проверка определённого вопроса или риска в режиме только чтения. |
| `Stage Brief` | Подготовка подробного файла задачи из принятых решений Stage, если он нужен. |
| `OPS Task` | Постановка задачи Codex и передача её в работу. |
| `Review` | Проверка результатов Codex: как аудита, так и основной задачи. |
| `Fix-loop` | Точечное исправление проблем, выявленных в Review. |
| `Commit` | Принятие результата и завершение работы Stage; фиксация изменений в Git применима при изменении репозитория. |

Не каждый Stage обязан проходить все фазы. Навигационная фаза сама по себе не выдаёт разрешения на действия.

## Architecture

`Architecture` — зрелость архитектурного решения, а не отдельная фаза рабочего процесса. Она независима от `Phase loop` и может сохраняться при смене действия.

| Состояние | Смысл |
|---|---|
| `N/A` | Архитектурной составляющей в текущем Stage нет. |
| `Existing` | Stage следует уже принятой архитектуре и существующим границам, нового решения не создаёт. |
| `Exploring` | Решение формируется или пересматривается: исследуются варианты, ответственность, границы и компромиссы с учётом фактов из репозитория. |
| `Proposed` | Command Center сформировал предварительное решение в Decision gate; оно ожидает принятия или дополнительной проверки. |
| `Assessed` | Дополнительная проверка по фактам из репозитория, совместимости, альтернативам и рискам действительно проведена, а её результат рассмотрен в Review. Это не утверждение архитектуры. |
| `Approved` | Command Center принял архитектурное решение в границах текущего Stage. |

Переходы не образуют обязательную линейную цепочку:

- `Exploring → Proposed → Approved` допустим без дополнительной проверки, если фактов достаточно и проверка не даёт существенного снижения риска.
- `Proposed → Assessed → Approved` применим, если дополнительная проверка действительно состоялась и была рассмотрена. Само наличие предложения или запланированного аудита не даёт `Assessed`.
- `N/A / Existing → Exploring` означает появление нового архитектурного вопроса; `Proposed / Assessed / Approved → Exploring` — необходимость пересмотра, в том числе из-за новых существенных фактов или изменения границ работы.

`Assessed ≠ Approved`. `Approved` устанавливает только Command Center; Codex и Reviewer не переводят архитектуру в это состояние. Если Stage создаёт или меняет архитектуру, переход к Stage Brief возможен после `Approved`; `Existing` и `N/A` не требуют нового утверждения архитектуры.

При нескольких архитектурных вопросах поле отражает агрегированную зрелость Stage: самое незрелое существенное состояние либо текущий критический вопрос.

## Навигационная плашка

| Поле | Как понимать |
|---|---|
| `Stage` | Номер и краткое название текущего крупного блока. |
| `Phase loop` | Текущая фаза работы из списка выше. |
| `Architecture` | Зрелость архитектурного решения Stage; при необходимости — короткое пояснение объекта решения. |
| `Current step` | Открытый Step внутри Stage. |
| `Current question` | Конкретный вопрос, который сейчас требуется закрыть или уточнить. |
| `Decision gate` | Условие следующего перехода: при `Step discussion` — закрытия Step; в фазе `Decision gate` — принятия сборного решения Stage, отправки на аудит или возврата вопроса в Step-loop. |
| `Position` | Место внутри Stage и состояние соседних Step: ⏳ ещё не начат, 🔵 активен, ✅ закрыт, 🟨 отложен, 🟥 заблокирован. |

`blocked` в `Position` — временная невозможность продолжить из-за недостающих данных, зависимости или отсутствия необходимого разрешения; это не состояние `Architecture`.

Навигационные плашки полезны Reviewer как предпочтительные смысловые ориентиры при восстановлении истории. Сама плашка не заменяет содержание обсуждения и основания решений.

## Codex Audit

Необязательная проверка репозитория, изменений, архитектурной границы, тестов, документации, альтернатив или рисков в режиме только чтения. Её предмет определяется текущим вопросом, границами задачи и целью аудита; она не ограничивается архитектурой.

Результат — замечания, подтверждающие материалы, альтернативы, риски и рекомендации, но не утверждение архитектуры и не разрешение на реализацию. После Review результата работа возвращается в `Decision gate`: Command Center принимает сборное решение либо возвращает отдельный вопрос в Step-loop.

## Stage Brief и OPS Task

`Stage Brief` — подробная спецификация конкретной задачи: принятые решения, цель, границы, существенные детали, ограничения и ожидаемые проверки. Он не заменяет общие правила репозитория и не расширяет разрешённые границы работы.

`OPS Task` — постановка задачи Codex. В крупном Stage она может ссылаться на Stage Brief, а в локальной задаче — содержать достаточную постановку сама. Файл `docs/codex/tasks/<task>.md`, сохранённый в репозитории и указанный в запросе, может служить исходной постановкой задачи для Codex; это не то же самое, что Stage Brief, подключаемый как уточняющая спецификация.

Эти документы не обязательны для каждого Stage. Stage Brief создаётся при необходимости подробной спецификации; OPS Task оформляется, если задача передаётся Codex. Полный контракт постановки принадлежит `OPS_CENTER_CODEX_PROTOCOL.md`.

## Изменения / Review / Fix-loop / Commit

Для задачи с изменением репозитория действует цикл:

```text
Codex изменяет репозиторий
→ Repo change handoff
→ Review
→ [Fix-loop → новый Repo change handoff → Review] при необходимости
→ финальная передача изменений из индекса
→ Commit, если применим и отдельно разрешён
```

`Repo change handoff` передаёт фактические изменения после каждой задачи на изменение репозитория, включая каждый Fix-loop: точные границы задачи, состояние Git, отдельный файл различий, статистику изменений, результат проверки файла различий, выполненные проверки и причины пропуска остальных, краткое описание результата и известные риски. Если набора различий недостаточно, для Review нужны сами файлы. Одно краткое описание результата не заменяет этот проверяемый материал.

Техническая база сравнения перед очередной задачей на изменение репозитория — состояние в индексе: индекс хранит состояние до задачи, рабочее дерево — состояние с текущими изменениями, обычный `git diff` — разницу между ними. Такая база не означает ни разрешения на реализацию, ни утверждения архитектуры, ни разрешения на Commit. Финальная передача изменений из индекса показывает все принимаемые по задаче изменения относительно `HEAD`.

В Review проверяется результат и принимаются явные решения по существенным замечаниям: исправить, принять риск, отложить с конкретной привязкой, выделить задачу, отклонить с причиной или сознательно не переносить. Если исправления не нужны, Fix-loop пропускается. Если репозиторий не менялся, фиксация изменений в Git не требуется.

## Границы полномочий

- Архитектурное решение и его утверждение остаются у Command Center, не у Codex или Reviewer.
- Краткое описание результата Codex не заменяет фактические доказательства состояния репозитория; отчёт не является источником истины.
- Аудит не выдаёт разрешения на реализацию; вывод проверки кода не является ни утверждением архитектуры, ни разрешением на реализацию, ни разрешением на Commit.
- Состояние репозитория нельзя выдумывать; факты, предположения и риски должны различаться при постановке задачи и Review.
- Добавление изменений в индекс, исключение их из индекса, Commit и отправка в удалённый репозиторий требуют явной инструкции; наличие различий, отчёта, базы сравнения или положительного результата проверки их не разрешает.

## Карта канонических источников

Если справочника недостаточно, нужный раздел читается адресно в подтверждённом каноническом репозитории Command Center из привязок активного проекта.

| Файл | Владелец содержания |
|---|---|
| `Stage_Plan_Protocol.md` | Организация длительной работы через Stage, Gate, Decision gate, Architecture, Review/Fix-loop и Repo change handoff. |
| `OPS_CENTER_CODEX_PROTOCOL.md` | Постановка задач Codex и Review результата. |
| `Command_Center_Role.md` | Инженерная роль ChatGPT. |
| `Architecture_Reasoning_Guide.md` | Вспомогательная карта архитектурных вопросов и подходов; не задаёт рабочий процесс и не является источником истины проекта. |
| `Architecture_Map.md` | Структурная карта процесса работы в репозитории, ответственности отдельных слоёв и расположения артефактов. |
| `AGENTS.md` | Точка входа, маршрутизация и границы полномочий Codex в каноническом репозитории. |

Материалы о маршрутах, навыках и агентах канонического репозитория читаются адресно только тогда, когда конкретная проверка требует этих деталей. Их наличие в источнике не делает их частью ReviewerHub.

## Расхождения с источником

При расхождении этого справочника с каноническим источником приоритет имеет источник. Reviewer сообщает пользователю о расхождении; при обычной проверке справочник автоматически не переписывается.
